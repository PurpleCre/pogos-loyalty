## Error reporting and incident records

Client JS reporting is disabled until an isolated environment destination and exact public opt-in are configured. The new [reporting policy](../monitoring-safety-sprint.md) replaces recursive field-name redaction with a bounded error allowlist and an outgoing-envelope filter. Native crash capture, screenshots/hierarchy, replay, logs, sessions and tracing are disabled. Current checks use an injected transport; actual native/provider/network metadata and retained records still require review. New filtering does not erase historical Sentry/native data or change installed older clients. Approve provider access/region/retention/deletion and restricted incident-record handling through the [operational runbook](../operations-monitoring-runbook.md) before activation.

## Core minimisation follow-on

Milestone 3 now includes a **default-disabled, service-only core minimisation operation**, field/policy validation, financial invariants, immutable recovery receipts and separate retained/unstructured-record review. The full local suite passes **380 tests**. ## What is ready locally

Customers can open Profile → Privacy, account export and deletion. They can verify their password, prepare an account JSON export, change email marketing preferences, submit a deletion request, cancel a request before processing, and view their request’s public updates. Guest-accessible `/privacy-policy` and `/account-deletion` routes provide the contact and request entry points on native and web. The policy route renders an approved database notice when configured and accurately says it is unavailable otherwise. No controller identity, retention period or response deadline is invented.

Exports use 29 explicit sections and a server-owned cursor/progress record. They include caller-owned account/profile, locations, preferences/consents, quotes/orders/items/statuses/receipts, transactions/ledger/rewards, legacy notification/device metadata, achievements/referrals/gifts, POS links/activity, staff membership/invitation/access metadata, privacy requests, own branch-command summaries, transactional inbox, native-device metadata and the caller’s own finance-action metadata. Big integer balances and minor-unit values are represented as strings where appropriate. They omit auth/MFA credentials, bearer reward claims, push tokens/proof hashes/keys/endpoints, integration secrets, other people’s contacts and internal audit notes/raw vendor payloads. Branch operation reasons/request payloads, internal financial observations and other operators' identities are excluded; access to personnel/branch finance evidence needs reviewer assessment. The file states its customer-account scope; requests for other personnel/security/vendor records need reviewer assessment. Legacy notification delivery labels are historical assertions, not proven provider/device delivery.

Creation timestamps form an export cutoff. Pages are reads at their respective execution times, not a point-in-time database backup; mutable records can reflect later updates. Incomplete exports can restart on the same active request. The client checks section/cutoff/cursor consistency, account identity and size limits (25,000 rows and five million JSON characters), and offers no partial file if collection fails. Larger records need a support-assisted export. An export marked completed means **prepared**, not proof that the OS or recipient saved it.

Native exports use a temporary app-cache JSON file and the OS share sheet; cleanup is attempted after sharing and at app startup/account changes. Finance report exports share the same temporary-file cleanup, including startup/account changes. Web exports use a Blob download and revoke its object URL. A destination app/browser download is a user-controlled copy outside this cleanup. FileSystem/Sharing add native dependencies and require a new binary; preserve fingerprint compatibility when using the existing OTA triggers. Physical sharing, backup exclusion, low-storage/error and process-kill checks remain required.

## Consent and delivery

Marketing email defaults off for new and historical accounts; no migration infers opt-in from signup. Opt-in needs a verified email, the current approved notice version and explicit UI confirmation. Withdrawal does not require fresh-password verification and remains possible when a newer notice has not been published. Consent events are immutable and retries cannot overwrite a later withdrawal. The UI resets notice acknowledgement when the notice version changes.

The server recipient page includes only verified, current-version opt-ins and excludes deletion-processing/deleted accounts. The legacy marketing and AI support endpoints are held closed: historical `MARKETING_EMAIL_ENABLED` and `CUSTOMER_SUPPORT_AI_ENABLED` flags cannot activate them. A reviewed marketing implementation still needs consent/unsubscribe, transactional outbox, sender/domain, retry/idempotency and delivery acceptance. Automated support needs reviewed knowledge, limits and privacy/subprocessor handling. Prior selected/in-flight sends cannot be recalled by a later withdrawal; a closed endpoint does not erase historical vendor data. See the [Edge runtime sprint](../edge-runtime-sprint.md).

Client error logging now emits fixed operation labels and bounded machine codes instead of database error details, which can repeat personal input. Sentry events/breadcrumbs drop personal payload/context/request fields and scrub auth URL parameters/credential strings while retaining stack locations. This is a minimisation control, not a claim that monitoring, device identifiers or provider retention have received approval.

## Identity and request boundaries

Export/deletion submission requires a password authentication-method timestamp in the signed JWT from the last five minutes. A fresh `iat`/refresh token alone is insufficient. Staff/manager/finance/admin users and customers with enrolled MFA must also have AAL2. Password recovery is not a substitute for this proof; users sign in again after recovery. Existing database/account checks, caller-pinned tokens and account-scoped UI protect against account switching. These tests simulate claims locally; hosted JWT/Auth acceptance is still required.

Reviewers must be explicitly assigned in `privacy_reviewers`, have administrator scope and complete MFA. No reviewer is seeded. General administrators cannot read the queue or approve their own request. Public customer updates exclude internal reasons and system receipts. API accounts cannot directly edit consent, request, task or approval tables; histories/notices/retention approvals are immutable.

Submitting deletion records intent without erasing or disabling the account. Requests persist even when blocked by active customer orders/unsettled cash, staff cash custody, active reward holds/claims, staff/manager/finance/admin responsibilities, or missing policy approval. The reviewer must resolve these conditions rather than dropping financial records or the last administrator.

Starting approved processing freezes new cash quotes/orders, reward reservations/operations, invitation acceptance and direct application-table writes for that account; controlled privacy withdrawal/status operations remain available. These entrypoints and reviewer start share an account lock; a real PostgreSQL race rehearsal remains necessary. Cancelling is permitted before processing only; after processing starts, contact the privacy team because partial erasure may already have occurred. Pausing keeps the account frozen. Resume rechecks blockers and approvals; changed notice/retention versions invalidate prior system-task evidence.

## Reviewed processing and completion

1. In Admin → Privacy requests, an assigned reviewer identifies the case, checks the requester/operational state and records a reason. Start checks blockers again and captures the approved notice/retention versions. No physical erasure occurs merely by pressing Start.
2. The authorised server-side operator follows the approved executable procedure, including disabling/revoking Auth access before scrubbing and verifying that the provider rejects subsequent profile/metadata changes. Complete every applicable field/store/vendor action; retain only the minimal records and evidence explicitly approved. Review immutable audit notes, actor references, quotes/command snapshots and historical raw payloads as well as obvious contact fields. Financial FKs/triggers make a blind `auth.users`/profile cascade unsafe.
3. For Auth, use the separately reviewed server-side deletion path. Supabase’s soft-delete option is irreversible and preserves hashed identification; it must be assessed together with the retained application records, not treated as complete application erasure. Never expose a service key or call auth-admin deletion from a customer client. [Supabase deletion API](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser)
4. After the separately reviewed provider step, run `minimize_privacy_application` with the current case/policy, a stable run UUID, named operator and row budget. Resolve uncertain/in-flight notification delivery first. Complete the residual/unstructured-record review, then record actual matching evidence with `attest_privacy_application_review`; a run alone cannot complete the application task. Record actual evidence for `application`, `authentication`, `gaap`, `email`, `monitoring` and `backups` through server-only `record_privacy_task`. An inapplicable vendor needs an owned, documented inventory/retention justification; a disabled feature flag does not prove that no historical data exists. Application/Auth cannot be marked inapplicable. For pending backup expiry, follow the approved restore-suppression/expiry plan and record its real schedule/evidence; do not claim the backup is already erased.
5. Server-only `complete_privacy_deletion` checks captured/current approvals, case version, all six task records, the current core run and matching retained-record review/task evidence, Auth’s deletion flag, cleared core profile/contact/device/link data, revoked staff access and resolved trading/cash/reward obligations. It does **not independently prove unstructured or vendor erasure**: the procedure and accountable receipts supply that evidence. No client/reviewer button can bypass completion. Do not record completion before the approved work is actually done.
6. A completed request becomes an access tombstone: restrictive policies deny stale-token private reads/writes and protected commands, and the app’s account-state check signs out the old identity. Retained financial records are not cascade-deleted. Local saved addresses, saved cart selections and known legacy personal caches are cleared on ordinary logout using guarded/serialized writes; financial recovery checkpoints survive normal logout and are removed only when completed deletion is detected. No device/backup forensic-erasure guarantee is implied.
7. Confirm completion through the approved support channel before removing the remaining contact route. Document residual retained categories/deadlines, vendor receipts, backup suppression/expiry and any exceptions; complete them under the approved schedule. Account deletion must remove non-retained associated data, not merely disable login.

## Offline storage follow-on

The [offline/lifecycle increment](../offline-launch-ux-milestone.md) adds validated account/environment cart selections and whitelisted public menu/branch snapshots. Cart records contain selection IDs/labels and estimated prices, not contact/address fields or credentials. Public snapshots are usable for at most 24 hours and always need online revalidation; this does not establish an erasure deadline. Private points/order reads remain in memory. Unknown `offline_pending_actions` evidence is preserved without automatic replay or deletion because ownership and successful processing cannot be established. Include historical installations/caches in the approved inventory and minimisation procedure. Existing ordinary logout preserves financial journals; authenticated order confirmation retires only matching branch selections before journal cleanup. OS/browser backups, recipient-controlled copies and forensic erasure remain separate acceptance questions.
