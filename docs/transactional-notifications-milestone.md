## Implemented scope

- **Trusted event outbox:** committed order-status and reward events create unique, recipient-bound in-app updates in the same transaction. Initial quoted cash orders also notify currently assigned staff/admins for that branch. Replaying an order/reward command does not create another source event; rolling back the transaction leaves no notification behind. Cash-custody-only changes do not spam customers. Historical events are not backfilled.
- **Native installation lifecycle:** explicit opt-in obtains the Expo token using the app's configured EAS project. A per-environment installation ID and random proof are persisted in SecureStore before registration, with no plaintext fallback. The database stores a hash and requires the same proof to rebind an installation. A token cannot simply be assigned to a different installation. Proof continuity is not hardware attestation or independent proof that an arbitrary submitted token belongs to an Expo project; real SDK/provider acceptance remains necessary.
- **Withdrawal and account changes:** local withdrawal commits before network unregistration; failed revocation remains recoverable for that account. Auth logout, direct account changes and completed-deletion detection attempt pinned-token cleanup. Foreground/token-change refresh renews an opted-in registration without prompting again. Registration expires after seven days; privileged recipients also need registration with MFA within the last 24 hours. Opening the attended staff app refreshes that evidence. These are technical limits pending operational acceptance.
- **Leased delivery worker:** a service-only claim API materialises deliveries for eligible devices bound before the event, leases bounded batches and uses an atomic dispatch fence. Repeated preparation cannot dispatch the same claim twice. Paused service, account deletion, changed device generation/project, expiry and staff revocation are rechecked before a send. The internal Edge Function uses a dedicated scheduler secret, an Expo access token, fixed HTTPS endpoints, bounded concurrency, timeouts and bounded response parsing. Caller input cannot supply recipients or message text.
- **Honest delivery evidence:** Expo tickets enter `ticket`; later receipts can enter `provider_accepted`. Neither means the customer/device displayed or read a notification. Rate-limit/provider errors back off with at most five send attempts. Missing receipts are polled separately, beginning after 15 minutes and bounded to 20 checks. Network ambiguity or a dispatched lease abandoned by a crashed worker becomes `unknown`, with no automatic blind resend. HTTP retry/provider behavior can still produce duplicates; exactly-once device delivery is not claimed. [Expo sending and receipt semantics](https://docs.expo.dev/push-notifications/sending-notifications/)
- **Invalid tokens and exceptions:** `DeviceNotRegistered` retires only the captured device generation, protecting a newer token/account binding. MFA administrators can inspect masked delivery health and review unknown outcomes after recent password verification. A resend requires explicit acceptance of duplicate-notification risk, a reason and the current version; expired/ineligible/exhausted events cannot be resent. Results and review evidence are immutable to API callers.
- **Inbox and routing:** Profile → Order updates and device notifications contains an account-scoped, paginated inbox available independently of push. Taps carry only a closed kind plus recipient/event IDs. Warm/cold responses are deduplicated and revalidated through an owner/current-permission RPC before a fixed app route opens. Order updates open tracking; staff updates open the correct branch queue; rewards open the customer's reward collection screen. No notification-provided URL is followed. Staff taps open a branch queue rather than selecting a specific order card.
- **Privacy and legacy containment:** native banners contain generic text and no customer name, address, phone, amount, QR secret or order details. Foreground mismatched-account payloads are suppressed. The old arbitrary-recipient VAPID/Capacitor handler now returns 410 instead of recording fake delivery. New direct legacy subscription/notification writes are revoked. The inventory covers **64 public tables**, and exports have **28 sections**, including owned update/device metadata without tokens, proof hashes, provider payloads or other recipients. Erasure completion now also rejects retained device bindings and recipient events; an inactive token alone is not erasure.

The migration is `20261102000001_transactional_notifications.sql`. It creates five tables and narrow RPCs/triggers; it does not add a hosted schedule or activate a project. No package dependency was added.

Apply the migration before an app update starts calling its APIs. Retire the deployed legacy sender explicitly: SQL migration alone does not replace an already-deployed Edge Function.
2. Bind `push_settings.expo_project_id` to the reviewed environment's EAS project while keeping `enabled=false`. The app-supplied project must match it. Do not enable a current development account as Pogo's production service by assumption. Build/install the matching runtime and configure/test FCM/APNs credentials in the correct Expo/store accounts.
3. Deploy the worker with `TRANSACTIONAL_PUSH_ENABLED=false`, a unique random `PUSH_WORKER_SECRET` of at least 32 characters and the server-only `EXPO_PUSH_ACCESS_TOKEN`. Enable the corresponding Expo push access-token security setting. Never expose these in public app variables. `verify_jwt=false` is intentional only for this internal scheduler endpoint: the handler must reject an absent/wrong `X-Worker-Key` before any database claim. Test wrong-key/customer/anonymous and disabled-state cases in the actual Deno/gateway runtime.
4. Configure an authenticated protected scheduler calling the worker using POST and the secret header. No schedule is installed by this migration. The handler claims 10 jobs per call, with at most four concurrent provider requests; the SQL API allows a maximum batch of 20. Agree cadence/capacity from measured multi-branch demand, receipt workloads and provider limits. Monitor the oldest pending row, retries, unknown/failed counts, lease expiry, missing receipts and scheduler failures; route alerts to named owners.

No automatic erasure worker or retention approval is supplied here.
6. Use opted-in internal test devices and enable the server switch plus the database switch in the isolated environment. Set `enabled_since` to the agreed activation time when enabling; earlier events must not be blasted as a backlog. Keep real customer activation gated. 7. Rehearse registration, denied/revoked permissions, token rotation, reinstall/corrupt storage, logout offline/online, A→B account changes, shared devices, old notifications, MFA/revocation/deletion, foreground/background/terminated launches, duplicate taps, wrong recipients, expired sessions, receipt absence, invalid tokens and worker crashes. ## Explicit operational boundaries

Push supplements the live order/branch queue; it must not be the only way a branch notices an accepted customer order. The inbox is transactional history, not proof of device reception. Device OS/network behavior and an already-submitted provider request cannot be revoked synchronously. During an offline logout, local presentation/routing is suppressed and revocation is retained for retry, but an in-flight or unrevoked background notification can still arrive with generic text until the server binding is revoked, replaced or expires. Do not promise instantaneous provider recall.

The first release supplies Android/iOS Expo push and an in-app inbox. Browser push, arbitrary broadcasts, marketing campaigns, SMS and AI notifications remain disabled/deferred. Unreadable proof storage, reinstall/token collisions and permanent authorisation failures require an owned support/recovery procedure; do not overwrite a proof or delete historical evidence blindly.

The next independent implementation area is granular manager/finance permissions and reconciliation/reporting completion, alongside the outstanding client decisions, hosted acceptance and hardening work. This increment does not close Phase 6 or the overall production gate.
